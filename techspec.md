# Парсер событий Прометей (+ нормализатор данных)

## *вольное описание*


---

## 1. Цель и контекст

Модуль `mpei_events_extractor` позволяет спарсить События с учебной платформы Прометей по API, нормализовать их 
(в `.json`-файл с требуемыми полями) и использовать дальше с другими модулями (например, по шаблону заполнить папку 
в obsidian vault с учебными заметками или создать на каждое Событие Мероприятие в google календаре). 

Приложение будет состоять из модуля-экстрактора и любых других модулей стоящих после него в пайплайне.

## 4. Данные и контракты

*точные форматы данных на входе и выходе: схемы API, внутренние модели, форматы файлов*

#### Контракт с API Прометея

###### запрос

У api Прометея нет каких-либо лимитов. Все данные можно получать по url `https://dot.mpei.ac.ru/close/ajax.asp`. 
Ограничение лишь в том, что при парсинге следует перебрать query-параметр `month` и `year` с начала семестра и 
до конца, чтобы получить все События, поскольку иначе платформа отдает только часть Событий.

Доступ к данным защищён сессионной кукой ASPSESSIONID* (конкретное имя куки зависит от того, какой сервер веб-фермы 
обработал запрос, и может отличаться от сессии к сессии) - без неё сервер отдаёт пустой ответ. В данном проекте кука 
выдаётся в момент авторизации и переиспользуется во всех последующих запросах в рамках одного прогона.

Ниже указан пайплайн запросов, достаточный для парсинга данных (при реальной работе браузера используется больше 
сторонних запросов). Подробнее о чувствительных данных см. п.6

1. Запрос отправки кредов пользователя и получения в ответ куки сессии
```text
POST https://dot.mpei.ac.ru/close/auth.asp?action=enter
Content-Type: application/x-www-form-urlencoded

ustatus:
returl:
AuthLogin:$LOGIN
AuthPassword:$PASS
```
из ответа этого запроса следует забрать `Set-Cookie`; полученного куки сессии достаточно на все время работы экстрактора

2. Запрос получения Событий (его следует парсить, подбирая `month` и `year`):
```text
GET https://dot.mpei.ac.ru/close/ajax.asp?action=get_events_and_accesses&year={year}&month={month}
Referer: https://dot.mpei.ac.ru/close/students/info.asp
X-Requested-With: XMLHttpRequest
Cookie: ASPSESSIONID*=SESSION_COOKIE
```

\* Примечание: знак `$` означает, что значение хранится в переменных окружения (см. п.6 - Безопасность)

###### ответ

Пример объекта События, отдаваемого Прометеем:

```xml
<item>
    <eventType>event</eventType>
    <eventName>КМ-1. Тестирование</eventName>
    <eventDateBegin>19.09.2026 00:00</eventDateBegin>
    <eventDateEnd>25.09.2026 23:59</eventDateEnd>
    <eventSubType>4</eventSubType>
    <eventIsNow></eventIsNow>
    <orderId>{90D67EBA-8B8D-44D9-82DF-6D024EC63887}</orderId>
    <courseId>{0461BCE1-27AF-4576-AFEB-F21EECE81502}</courseId>
    <courseName>Дифференциальные уравнения (ИДДО ДУ-Б-5-1-Экз)</courseName>
    <elementId>{3A4C1CE6-ACCD-49D2-81F5-1FC27580951B}</elementId>
    <elementType>t</elementType>
    <elementName>КМ-1. Дифференциальные уравнения 1-го порядка. Тестирование</elementName>
    <elementLinks></elementLinks>
</item>
```

Правило фильтрации: валидным Событием считается только `item`, у которого `eventType == "event"`. Значение 
`eventType == "access"` - служебная запись о доступе к тесту (не само учебное мероприятие) и должна отбрасываться 
нормализатором до попытки построить модель `Event`.

В отдаваемых api Прометея данных гарантированно `eventDateBegin` будет со временем 00:00, а `eventDateEnd` - 23:59. 
Поэтому в нормализованной модели эти значения хранятся без времени, только как дата (см. модель ниже).

Маппинг типа события (число) и самого события:
```text
4 = Тестирование
210 = Эссе / Контрольная работа
3 = ?
9 = ?
```

#### Внутренняя модель
 
```python
from pydantic import BaseModel
from uuid import UUID
from datetime import date
from typing import Literal
 
class Course(BaseModel):
    id_: UUID           # соответствует courseId
    name: str           # соответствует courseName очищ
 
class Event(BaseModel):
    id_: UUID           # соответствует elementId; также служит ключом для дедупликации
    name: str           # соответствует elementName очищ
    type_: Literal['Тестирование', 'Экзамен тест', 'Письменная работа', 'Экзамен письм. работа']
    # ^ маппинг из сырых полей (elementType/eventSubType) пока не выведен полностью -
    #   см. "Технические решения" п.7 и открытый вопрос 10
    date_start: date    # соответствует eventDateBegin; время отбрасывается (см. правило выше)
    date_end: date      # соответствует eventDateEnd; время отбрасывается (см. правило выше)
    course: Course
```

#### Формат выходного файла
 
Именоваться выходной файл `.json` должен по формату `{YYYY-MM-DD}.json`. Формат содержимого должен соответствовать 
автоматической выгрузке `pydantic`-модели в `JSON`.
 
На выход экстрактор должен отдавать `.json`, если был запущен непосредственно он (не импортирован в модуль-потребитель). 
В дальнейшем, когда экстрактор будет упакован в библиотеку, при импорте он должен отдавать список моделей `Event`. 
В обоих режимах используется один и тот же формат данных — модель `Event`, описанная выше.

#### Технические решения

1. Гарантия отсутствия дубликатов Событий *в рамках одного запуска* - за счёт использования поля `elementId` 
(`id_` в модели) как уникального ключа. Политика дедупликации между несколькими запусками - см. п.5
2. Нормализатор данных должен очищать и валидировать данные. Например, очищать имя События от "Тестирование" и подобное, 
очищать наименование курса от данных в скобках, валидировать дата-время и uuid
3. Логирование - с помощью `loguru`
4. Парсинг - с помощью `httpx` и `lxml`
5. Нормализация - с помощью модели События и `pydantic`
6. Тип События не содержится в конкретном поле, нужно вычленять из полей `elementName` и других; либо еще можно маппить 
из `eventSubType`, но нужно больше статистики
7. Поскольку url'ы до эндпоинта авторизации и получения Событий не меняются продолжительное время, то и храниться в 
конкретном файле они не будут, а только в качестве констант в коде
8. До упаковки в библиотеку оркестрацией модулей парсера и нормализатора занимается `main.py`
9. Оформление в библиотеку подразумевает, что будет создан отдельный файл с `pipeline.py`, в котором должен 
контролироваться вызов модулей парсера и нормализатора и передача параметров между ними
10. Файлы констант `config.py` (изменяемые настройки в зависимости от пользователя или других обстоятельств (креды) 
и требующие валидации) и `constants.py` (постоянные значения независимые от окружения)
11. API отдает данные в кодировке `cp-1251`


## 5. Бизнес-правила и ограничения

*описание случаев (границ) и поведения приложения при них, неочевидные из user stories; обычно выводятся из "а что если"*

Запуск планируется **ежесеместрово вручную**.

Если какие-то События будут добавляться сильно после начала семестра, то парсер с модулем-потребителем 
можно будет запустить повторно. В таком случае старые записи (прошлые `{YYYY-MM-DD}.json` файлы, см. п.4) не должны 
быть затёрты, а также должны быть корректно добавлены все новые.

Поскольку при повторном запуске посреди семестра экстрактор не знает о содержимом предыдущих запусков (каждый запуск - 
новый файл), дедупликация между несколькими запусками - зона ответственности модуля-потребителя. Дедупликация внутри 
одного запуска (см. п.4, "Технические решения" п.1) - зона ответственности экстрактора.

Предполагается (исходя из наблюдаемого поведения платформы, а не как гарантия с нашей стороны), что после начала 
семестра никакие События не будут удалены из Прометея.

Для написания модулей-потребителей в дальнейшем у экстрактора должны быть строго прописаны контракты и правила 
интеграции, по которым реализующий модуль сможет работать гарантированно корректно.

Все События, что не проходят по ожидаемому формату (описанному в модели), пропускать, логгируя ошибку.


#### Возможные ошибки

- отсутствие `.env` / пустой `.env` / отсутствие конкретных переменных
- сетевая недоступность ресурса
- проблемы с записью файла json


## 6. Нефункц. требования

*как система должна себя вести, а не что делать: скорость, надёжность, безопасность, тестируемость, переносимость*

- **Производительность**: обработка всех Событий пользователя за один прогон укладывается в разумное время (секунды, 
не минуты) - не критично для личного скрипта, но не должно "зависать"
- **Надёжность**: сетевые сбои и ошибки авторизации не должны ронять весь процесс без понятного сообщения; базовый retry 
на сетевые запросы
- **Переносимость**: Python 3.12, без ОС-специфичных зависимостей
- **Тестируемость**: `normalize` - чистая функция, покрывается unit-тестами без сети; `parser` мокируется в тестах
- **Логирование**: минимум `INFO` (шаги пайплайна) и `ERROR` (сбои); без секретов в логах
- **Безопасность**: креды и токены не коммитятся, `.env` в `.gitignore`; к чувствительным данным относятся путь до 
Obsidian vault, логин и пароль к учебной платформе
